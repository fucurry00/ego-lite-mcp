# ego-lite MCP サーバの設計

導入手順は [README](../README.md) にある。
ここには、サーバの構成と、各判断の理由・経緯を残す。

## 用語

- **ego (lite)**: Chromium ベースのブラウザ。AI エージェントに、利用者自身のログイン済みセッションを共有させることを目的とする。ローカル実行、配布は macOS 向けのみ。
- **MCP (Model Context Protocol)**: AI クライアントが外部ツールを呼び出すための通信規約。Claude Desktop はこの規約でローカルのサーバプロセスを子プロセスとして起動し、標準入出力で通信する。
- **skill**: エージェントに手順を与える形式。実行そのものは行わず、エージェント側の実行手段（シェル等）に依存する。

## なぜ必要か

ego lite 公式が配布している `ego-browser` は skill 形式だが、中身はシェルコマンドの実行手順である。
公式が対応エージェントとして挙げているのは Claude Code・Codex・Cursor など、いずれもローカルでシェルを実行できる CLI エージェントである。
Claude Desktop 単体にはシェル実行の経路がないため、skill を入れても実行段が存在しない。
この欠けている実行段を埋めるのが、この MCP サーバの役割である。

ego lite の制御は `ego-browser` に JavaScript を渡す形になっているため、CDP (Chrome DevTools Protocol) を自前で喋る必要はない。
CLI を起動するだけの薄いサーバで成立する。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `server.mjs` | MCP サーバ本体 |
| `test.mjs` | 標準入出力越しの疎通確認 |
| `docs/` | 設計文書と解説 |

手元では、リポジトリ直下に `~/.agents/skills/ego-browser` へのシンボリックリンク `ego-browser-skill` を置いてもよい。
リンク先が利用者のホームディレクトリの絶対パスになるため、`.gitignore` で追跡から外している。

## ツールは任意の実行と固定の実行の 2 本

| ツール | 受け取るもの | 想定する許可設定 |
|---|---|---|
| `ego_run_script` | Claude がその場で書いた JavaScript | その都度確認 |
| `ego_run_saved_script` | 保存済みスクリプトの名前だけ | 常に許可 |

`ego_run_script` は、JavaScript のソース文字列を受け取り、`ego-browser nodejs` の標準入力へ渡して、`console.log()` の出力を返す。
スクリプトは ego-browser に組み込まれた Node.js で動くので、ブラウザ操作に加えて、`node:fs` で手元のファイルを読み書きでき、`fetch` で外部に送ることもできる。

`ego_run_saved_script` は、実行用の場所（`~/.config/ego-lite-mcp/scripts/`）に置かれた `<名前>.js` を読み、`ego_run_script` と同じ処理で実行する。
引数は名前だけなので、Claude は実行するスクリプトを選べるが、中身は変えられない。
名前を省くと、置かれているスクリプトの名前の一覧を返す。
2 本に分けた理由は [ADR 0001](adr/0001-split-always-allowed-read-only-tools.md) と [ADR 0003](adr/0003-saved-scripts.md)、運用の規則は「保存済みスクリプト」の節にある。

操作ごとにツールを分ける案（`ego_navigate`、`ego_click`、`ego_snapshot` など）は採らなかった。
1 操作ごとにプロセス起動のオーバーヘッドが乗るうえ、ego lite の設計思想は「複数操作をまとめた 1 本のスクリプトを一度に流す」ことなので、速度面で逆行する。

## API の説明をこのサーバに書き写さない

任意の JavaScript を受け取るツールの欠点は、本来なら「ヘルパー一覧と使い方をツールの説明文に全て書き込む必要がある」ことにある。
しかし ego-browser の実行環境には `help()` が組み込まれており、API の説明文を実行時に返すため、この欠点は成立しない。

```bash
ego-browser nodejs -e 'await help()'             # 全 API、14,603 文字
ego-browser nodejs -e 'await help("taskSpace")'  # 1 項目のみ
```

`help()` は自分で出力したうえで同じ文字列を返すので、`console.log()` で包むと 2 回出力される。
ツールの説明文には `await help()` を呼ぶよう指示するだけでよい。
本体が `ego-browser upgrade` で新しくなれば、返る内容も自動的に新しくなる。

**この方針を採った理由は、書き写しによる食い違いを一度起こしたためである。**
2026-09-14 時点の検討メモは、公式サイト（https://lite.ego.app/document/en/docs/ego-browser）の記述から `useOrCreateTaskSpace()` / `openOrReuseTab()` / `snapshotText()` / `cliLog()` という API 一覧を書き写していた。
実際にインストールされていた ego-browser（公式スキル文書は version 2.0.0、2026-09-09 付）の API は `taskSpace()` / `task.page()` / `page.goto()` / `page.snapshot()` / `console.log()` であり、一致しなかった。
名前が違うだけでなく、実物はページ単位の操作、ポップアップとダイアログの受領情報、ファイルのダウンロード、ユーザーへの操作権の受け渡し（`handOff()`）まで含む。

運用上の約束事（1 ゴールにつき 1 タスクスペース、観測は必要最小限、完了時の `finish({ keep: [] })` など）は `help()` には含まれず、`ego-browser skill` の出力（手順の本文）にのみある。
`~/.agents/skills/ego-browser/SKILL.md` は、version 2.1.0 から「`ego-browser skill` を実行してその出力に従え」という案内だけになった。
これも複製せず、作業の開始時にサーバが `ego-browser skill` を実行し、その出力を結果に添付する（次節）。

## 運用手順は作業の開始時に結果へ添付する

当初は、ツールの説明文で「最初に `help()` と SKILL.md を読め」と案内していた。
2026-10-15 に Chat で試すと、モデルはどちらも読まず、説明文の最小例だけで作業を始めた。
`page.screenshot?.()` のように API の有無を疑う書き方や、Chat からは見られない `/tmp` への画像保存が出ていた。
説明文に動く最小例があると、案内は読み飛ばされる。

そこで、作業の開始にあたる呼び出しでは、サーバが手順の本文（`ego-browser skill` の出力）を結果に付けて返す。
SKILL.md のファイルを添付していた時期もあるが、SKILL.md が案内だけになったため、シェルのない Chat/Cowork では従えなくなった（https://github.com/fucurry00/ego-lite-mcp/issues/10）。
作業の開始は、スクリプトに次のいずれかを含む呼び出しとする。

- `taskSpace("…")`（文字列での新規作成）
- `listTaskSpaces` / `claimTaskSpace` / `takeOverTaskSpace`（利用者のスペースへの介入）

`taskSpace(23)` のような数値 ID での再開には付けない。
説明文からは最小例を削り、最初の呼び出しを「タスクスペースを作って ID を出すだけ」に誘導している。

判定をスクリプトの文字列で行うのは、サーバが「どの会話からの呼び出しか」を受け取れないためである。
Claude Desktop はサーバの 1 プロセスを複数の会話で使い回すので、「プロセス内の初回」で判定すると会話ごとの初回にならない。
変数経由の `taskSpace(name)` は取りこぼすが、説明文の誘導で最初の呼び出しはリテラルになる想定である。

採らなかった案は次のとおり。

- MCP の `instructions` に手順の本文を入れる案。確実だが、ブラウザと無関係な会話にも約 2 万字が常に乗る。Code の skill は本文を起動時にしか読まないので、それより重い。
- 引数 `first_call` をモデルに申告させる案。判定がモデル任せになる。
- 手順を返す専用ツールを足す案。呼ぶかどうかがモデル任せになる。

手順の本文は CLI 前提で書かれているため、添付時に MCP 用の読み替えを数行前置きする。
heredoc などの代わりに `script` 引数へ渡すこと、`ego-browser upgrade` などほかのコマンドは利用者に実行を頼むこと、`references/` の絶対パス、保存した画像は見られないので `snapshot()` で観測すること、の 4 点である。
画像を結果に添付する機能は https://github.com/fucurry00/ego-lite-mcp/issues/1 に残してある。

Desktop の Code タブでは、`~/.claude/skills/ego-browser`（ego lite のオンボーディングが作る）と、この MCP の両方が見える。
どちらを使っても手順は届くので、片方を外す設定はしていない。
両方を使うと手順の本文が 2 回読み込まれるが、それは許容している。

## 書き込み操作の扱いと許可設定

ログイン済みセッションをそのまま使う設計のため、書き込み操作も、送信・購入・削除のような取り消せない書き込みも実行できる。
これをサーバ側では止めない。
`ego_run_script` については、Claude Desktop がツール呼び出しの前に出す承認画面に、実行されるスクリプトの全文が表示されるので、利用者が読んでから許可できる。

**この安全策は、`ego_run_script` を「その都度確認」にしている場合にしか働かない。**
2026-10-27 に利用者の設定画面を確かめると、`ego_run_script` は「常に許可」になっており、承認画面は出ていなかった（ADR 0001）。
そこで、許可設定を次のように分ける。

- `ego_run_saved_script` だけを「常に許可」にする。中身の確認は、実行のたびではなく、配置のときに 1 回だけ行う（ADR 0003）。
- `ego_run_script` は「その都度確認」に戻す。書き込み操作が必要になるたびに確認が入るのは、意図した結果である。
- 無人実行（スケジュールタスク）は、`ego_run_saved_script` だけで完結するように作る。`ego_run_script` を呼ぶと承認待ちになり、実行されない。

常に許可の対象は 1 本のツールなので、実行用の場所に置いたすべてのスクリプトが、確認なしで動く。
そこに読み取り操作だけのスクリプトを置くことは、コードでは強制されず、配置のときの利用者の確認で守る。
`ego_run_saved_script` に付けた `readOnlyHint: true` も、この運用の規則を表すものであり、コードで保証したものではない。

以前の版は、日常の調べ物のために読み取り専用の固定のツールを別に立てることを「次の一手」として残していた。
保存済みスクリプトのツールが、その一手にあたる。

サーバ側で語句を検査して拒否する案（「送信」「Send」「購入」などを含んだら拒否する）は採らなかった。
要素番号（`@21` など）での指定に対して無力である一方、「送信ボタンを探す」だけの読み取り操作のスクリプトも誤って拒否するためである。

## 保存済みスクリプト

### 配置

スクリプトは非公開の git リポジトリで書き、利用者が中身を確かめてから、実行用の場所 `~/.config/ego-lite-mcp/scripts/` へコピーする。
このコピーを配置と呼ぶ。
どの版を承認したかを後から git で追えるよう、配置するのはコミット済みの版だけにする。

- **シンボリックリンクにしない。** リンクの先は、配置の承認を経ずに書き換わりうる。リンクの先がリポジトリのファイルなら、Claude による書き換えやコミットしていない変更が、常に許可のツールから確認なしで実行される。そのため、サーバはリンクとフォルダを一覧に出さず、名前で指定されても実行しない。
- **実行用の場所のフォルダ自体もリンクにしない。** この場合は、サーバのコードでは防いでいない。
- 名前は英小文字・数字・ハイフンだけで、64 文字までとする。それ以外の名前はサーバが拒否する。
- 実行用の場所には、承認したスクリプトだけを置く。スクリプトが読み書きする状態のファイルは、別の場所に置く。

テストのために実行用の場所を変えたいときは、サーバの環境変数 `EGO_SCRIPTS_DIR` で差し替える。

### 実行環境の制約

保存済みスクリプトは、利用者の手元の Node.js ではなく、ego lite のアプリの中の Node.js で動く。
2026-10-27 に、実行環境の値を出力するスクリプトで次のことを確かめた。

- 作業ディレクトリ（`process.cwd()`）は `/` である。相対パスは、スクリプトの置き場所ではなく `/` を基準に解決される。
- `import.meta.url` は `file:////[eval2]` である。スクリプトは標準入力から渡されるので、自分がどこに置かれているかを知れない。
- サーバに渡した環境変数（`EGO_SCRIPTS_DIR` など）は、スクリプトからは見えない。`HOME` は読める。

そのため、保存済みスクリプトは次のように書く。

- 1 つのスクリプトを 1 つのファイルで完結させる。隣に置いた補助のファイルは `import` で読み込めない。
- 読み書きするファイルは、`HOME`（`node:os` の `homedir()`）をもとにした絶対パスで指定する。実行のたびに書き換わる状態のファイルは、`~/.local/state/` の下のような、状態の置き場所に置く。`~/.ego` は ego lite 本体のデータ置き場なので使わない（ADR 0003）。
- 外から値を渡す手段はない。URL などの値は、スクリプトに直接書く。

### 失敗したときもタスクスペースを閉じる

保存済みスクリプトは、途中で失敗しても、開いたタスクスペースを閉じる。

```js
const task = await taskSpace("…");
try {
  // 読み取りと出力
} finally {
  await task.finish({ keep: [] });
}
```

閉じないと、誰も見ていない無人実行の後に、失敗したスペースが利用者のブラウザに残る。
さらに、`taskSpace(名前)` は同じ名前の自分のスペースを再開するので、次の実行は前回のページの状態から始まる。
2026-10-27 に、例外を投げるスクリプトを 2 回続けて実行し、1 回目のスペースが開いたまま残ることと、2 回目がそのスペースを再開することを確かめた。

ego-browser の手順の本文は、エラーで止まったときは `finish()` を呼ばないよう求めている。
これは、作業している Claude がその場で状態を見て立て直す前提の規則である。
保存済みスクリプトには立て直す者がいないので、この規則には従わない。
その代わり、失敗したときのページの状態は残らない。
例外の理由はツールの結果のエラー文として返るが、ページの状態が原因を知る手がかりになるなら、閉じる前にスクリプト自身が出力する（https://github.com/fucurry00/ego-lite-mcp/issues/9）。
2026-10-27 に、上の形で例外を投げるスクリプトを実行し、スペースが閉じることと、例外の理由が結果に返ることを確かめた。

### 既知の制限

- 同じスクリプトを同時に 2 つ実行すると、後から始まった方が「同じ名前のタスクスペースが既にある」というエラーで失敗する。
- 時間切れの後も、スクリプトは止まらずに動き続ける（https://github.com/fucurry00/ego-lite-mcp/issues/8）。

## タイムアウトと出力量

実行時間の上限を 180 秒、出力の上限を 100,000 文字とした。2 本のツールで共通である。
上限に達した場合は、切り詰めた旨と、出力を絞る具体的な手段（`snapshot({ scope: "subtree", root: "@N" })` など）を末尾に付ける。
この手段は、中身を変えられない保存済みスクリプトには使えない。

時間切れのときにサーバが止めるのは `ego-browser nodejs` のコマンドの処理だけで、スクリプト自体は動き続ける。
2026-10-27 に、185 秒後に印のファイルを書くスクリプトで確かめた（https://github.com/fucurry00/ego-lite-mcp/issues/8）。

## 出力の経路

ego-browser の埋め込み Node は、`console.log()` の出力を標準出力ではなく標準エラー出力に書く。
成功時の結果もそこに来るため、サーバは標準エラー出力を異常として扱わず、標準出力と連結して返す。

## エラー時の文言

標準エラー出力をそのまま返したうえで、原因に応じた一文を添える。
`ego-browser` が見つからない場合（ENOENT）は `EGO_BROWSER_BIN` の設定を促し、時間切れの場合は作業の分割を促し、それ以外は ego lite が起動していない可能性を挙げる。

接続できない場合に ego-browser 自身が返す文言は、ego lite が起動した状態で `--ego-server-name` に存在しない名前を渡して確認した。
`Failed to connect to ego_cli bootstrap` に続けて、ego lite.app を手動で起動するよう促す内容が返る。

なお、添える一文は ENOENT でも時間切れでもない全てのエラーに付く。
出力が 32MB を超えた場合（`maxBuffer` 超過）にも「ego lite が起動していない可能性がある」と表示され、原因を取り違えさせる。
発生確率が低いため分岐は足していない。

## 確認の記録

2026-09-16 に、README の動作確認の 2 段階がどちらも成功することを確認した。
デスクトップアプリが起動した子プロセスから ego lite の内部サービスに到達できており、懸念していたサンドボックスの制約には当たらなかった。
第 2 段階では example.com を開き、スナップショットを取得し、`finish({ keep: [] })` でタスクスペースを閉じるところまで通っている。

2026-10-27 に、`ego_run_saved_script` を MCP 経由で実際のブラウザで動かした。
ページを開いて読み、タスクスペースを閉じるスクリプトが約 3 秒で結果を返し、実行をまたいだ状態のファイルの読み書きも動いた。
このとき見つかった問題は、https://github.com/fucurry00/ego-lite-mcp/issues/8 から #11 に起票した。

2026-10-15 の比較検証（起動コスト、まとめ実行と分割実行の所要時間）は [ego-lite-control-layer.md](ego-lite-control-layer.md) にある。
この解説は SKILL.md 添付の導入前に書いたもので、ツール説明文の記述はその時点のものである。
