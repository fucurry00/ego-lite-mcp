# ego-lite MCP サーバの設計

導入手順は [README](../README.md) にある。
ここには、サーバの構成と、各判断の理由・経緯を残す。

## 用語

- **ego (lite)**: Chromium ベースのブラウザ。AI エージェントに、利用者自身のログイン済みセッションを共有させることを目的とする。ローカル実行、配布は macOS 向けのみ。
- **MCP (Model Context Protocol)**: AI クライアントが外部ツールを呼び出すための通信規約。Claude Desktop はこの規約でローカルのサーバプロセスを子プロセスとして起動し、標準入出力で通信する。
- **skill**: エージェントに手順を与える形式。実行そのものは行わず、エージェント側の実行手段（シェル等）に依存する。

## なぜ必要か

ego lite 公式が配布している `ego-browser` は skill 形式だが、中身はシェルコマンドの実行手順である。
公式が対応エージェントとして挙げているのは Claude Code・Codex・Cursor など、いずれもローカルでシェルを実行できる CLI エージェントである。
Claude Desktop 単体にはシェル実行の経路がないため、skill を入れても実行段が存在しない。
この欠けている実行段を埋めるのが、この MCP サーバの役割である。

ego lite の制御は `ego-browser` に JavaScript を渡す形になっているため、CDP (Chrome DevTools Protocol) を自前で喋る必要はない。
CLI を起動するだけの薄いサーバで成立する。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `server.mjs` | MCP サーバ本体 |
| `test.mjs` | 標準入出力越しの疎通確認 |
| `docs/` | 設計文書と解説 |

手元では、リポジトリ直下に `~/.agents/skills/ego-browser` へのシンボリックリンク `ego-browser-skill` を置いてもよい。
リンク先が利用者のホームディレクトリの絶対パスになるため、`.gitignore` で追跡から外している。

## ツールは `ego_run_script` の 1 本のみ

JavaScript のソース文字列を受け取り、そのまま `ego-browser nodejs` の標準入力へ流し、`console.log()` の出力を返す。

操作ごとにツールを分ける案（`ego_navigate`、`ego_click`、`ego_snapshot` など）は採らなかった。
1 操作ごとにプロセス起動のオーバーヘッドが乗るうえ、ego lite の設計思想は「複数操作をまとめた 1 本のスクリプトを一度に流す」ことなので、速度面で逆行する。

## API の説明をこのサーバに書き写さない

ツールを 1 本にする構成の欠点は、本来なら「ヘルパー一覧と使い方をツールの説明文に全て書き込む必要がある」ことにある。
しかし ego-browser の実行環境には `help()` が組み込まれており、API の説明文を実行時に返すため、この欠点は成立しない。

```bash
ego-browser nodejs -e 'console.log(await help())'             # 全 API、14,603 文字
ego-browser nodejs -e 'console.log(await help("taskSpace"))'  # 1 項目のみ
```

ツールの説明文には `await help()` を呼ぶよう指示するだけでよい。
本体が `ego-browser upgrade` で新しくなれば、返る内容も自動的に新しくなる。

**この方針を採った理由は、書き写しによる食い違いを一度起こしたためである。**
2026-09-14 時点の検討メモは、公式サイト（https://lite.ego.app/document/en/docs/ego-browser）の記述から `useOrCreateTaskSpace()` / `openOrReuseTab()` / `snapshotText()` / `cliLog()` という API 一覧を書き写していた。
実際にインストールされていた ego-browser（公式スキル文書は version 2.0.0、2026-09-09 付）の API は `taskSpace()` / `task.page()` / `page.goto()` / `page.snapshot()` / `console.log()` であり、一致しなかった。
名前が違うだけでなく、実物はページ単位の操作、ポップアップとダイアログの受領情報、ファイルのダウンロード、ユーザーへの操作権の受け渡し（`handOff()`）まで含む。

運用上の約束事（1 ゴールにつき 1 タスクスペース、観測は必要最小限、完了時の `finish({ keep: [] })` など）は `help()` には含まれず、`~/.agents/skills/ego-browser/SKILL.md` にのみある。
これも複製せず、作業の開始時にサーバが実行時に読み出して結果に添付する（次節）。

## 運用手順は作業の開始時に結果へ添付する

当初は、ツールの説明文で「最初に `help()` と SKILL.md を読め」と案内していた。
2026-10-15 に Chat で試すと、モデルはどちらも読まず、説明文の最小例だけで作業を始めた。
`page.screenshot?.()` のように API の有無を疑う書き方や、Chat からは見られない `/tmp` への画像保存が出ていた。
説明文に動く最小例があると、案内は読み飛ばされる。

そこで、作業の開始にあたる呼び出しでは、サーバが SKILL.md 本文を結果に付けて返す。
作業の開始は、スクリプトに次のいずれかを含む呼び出しとする。

- `taskSpace("…")`（文字列での新規作成）
- `listTaskSpaces` / `claimTaskSpace` / `takeOverTaskSpace`（利用者のスペースへの介入）

`taskSpace(23)` のような数値 ID での再開には付けない。
説明文からは最小例を削り、最初の呼び出しを「タスクスペースを作って ID を出すだけ」に誘導している。

判定をスクリプトの文字列で行うのは、サーバが「どの会話からの呼び出しか」を受け取れないためである。
Claude Desktop はサーバの 1 プロセスを複数の会話で使い回すので、「プロセス内の初回」で判定すると会話ごとの初回にならない。
変数経由の `taskSpace(name)` は取りこぼすが、説明文の誘導で最初の呼び出しはリテラルになる想定である。

採らなかった案は次のとおり。

- MCP の `instructions` に SKILL.md を入れる案。確実だが、ブラウザと無関係な会話にも約 2 万字が常に乗る。Code の skill は本文を起動時にしか読まないので、それより重い。
- 引数 `first_call` をモデルに申告させる案。判定がモデル任せになる。
- 手順を返す専用ツールを足す案。呼ぶかどうかがモデル任せになる。

SKILL.md は CLI 前提で書かれているため、添付時に MCP 用の読み替えを数行前置きする。
heredoc の代わりに `script` 引数へ渡すこと、`references/` の絶対パス、保存した画像は見られないので `snapshot()` で観測すること、の 3 点である。
画像を結果に添付する機能は https://github.com/fucurry00/ego-lite-mcp/issues/1 に残してある。

Desktop の Code タブでは、`~/.claude/skills/ego-browser`（ego lite のオンボーディングが作る）と、この MCP の両方が見える。
どちらを使っても手順は届くので、片方を外す設定はしていない。
両方を使うと SKILL.md が 2 回読み込まれるが、それは許容している。

## 危険操作の扱い

ログイン済みセッションをそのまま使う設計のため、送信・購入・削除に相当する操作が実行可能である。
これをサーバ側では止めない。
Claude Desktop はツール呼び出しの前に承認画面を出し、そこには実行されるスクリプトの全文が表示されるため、利用者が読んでから許可できる。

サーバ側で語句を検査して拒否する案（「送信」「Send」「購入」などを含んだら拒否する）は採らなかった。
要素番号（`@21` など）での指定に対して無力である一方、「送信ボタンを探す」だけの安全なスクリプトも誤って拒否するためである。

**この方針は `ego_run_script` を「常に許可」に設定しないことが前提である。** 設定した時点で歯止めがなくなる。
日常の調べ物で「常に許可」にしたくなった場合は、読み取り専用のツール（URL を受け取ってページ内容を返すだけの固定処理）を別に立て、そちらだけを「常に許可」にする。
これが次の一手として残してある判断である。

## タイムアウトと出力量

実行時間の上限を 180 秒、出力の上限を 100,000 文字とした。
上限に達した場合は、切り詰めた旨と、出力を絞る具体的な手段（`snapshot({ scope: "subtree", root: "@N" })` など）を末尾に付ける。

## 出力の経路

ego-browser の埋め込み Node は、`console.log()` の出力を標準出力ではなく標準エラー出力に書く。
成功時の結果もそこに来るため、サーバは標準エラー出力を異常として扱わず、標準出力と連結して返す。

## エラー時の文言

標準エラー出力をそのまま返したうえで、原因に応じた一文を添える。
`ego-browser` が見つからない場合（ENOENT）は `EGO_BROWSER_BIN` の設定を促し、時間切れの場合は作業の分割を促し、それ以外は ego lite が起動していない可能性を挙げる。

接続できない場合に ego-browser 自身が返す文言は、ego lite が起動した状態で `--ego-server-name` に存在しない名前を渡して確認した。
`Failed to connect to ego_cli bootstrap` に続けて、ego lite.app を手動で起動するよう促す内容が返る。

なお、添える一文は ENOENT でも時間切れでもない全てのエラーに付く。
出力が 32MB を超えた場合（`maxBuffer` 超過）にも「ego lite が起動していない可能性がある」と表示され、原因を取り違えさせる。
発生確率が低いため分岐は足していない。

## 確認の記録

2026-09-16 に、README の動作確認の 2 段階がどちらも成功することを確認した。
デスクトップアプリが起動した子プロセスから ego lite の内部サービスに到達できており、懸念していたサンドボックスの制約には当たらなかった。
第 2 段階では example.com を開き、スナップショットを取得し、`finish({ keep: [] })` でタスクスペースを閉じるところまで通っている。

2026-10-15 の比較検証（起動コスト、まとめ実行と分割実行の所要時間）は [ego-lite-control-layer.md](ego-lite-control-layer.md) にある。
この解説は SKILL.md 添付の導入前に書いたもので、ツール説明文の記述はその時点のものである。
